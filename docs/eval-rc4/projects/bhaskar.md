## 4. Findings

**BHASKAR-1: random-route calibration is measured at desktop only and applied to every size and to scroll states**
- Category B, partially improved (rc.3 C7). Stage: capture -> routes gate.
- Expected: an unstable route is held to its own worst self-match, so a correct clone can pass (C7 fix: ">= 3 self-loads, held to the minimum").
- Observed: capture compares 2 extra loads with the mask shot **only when `vp.name === 'desktop'`** (`CLI\capture.mjs:378-392`) and stores one number (`meta.json` `/playground` unstable 96.57). `report.mjs:213` applies `match - 1` = 95.57 to layout **and** states at all 5 sizes. Agent probe, same lib functions: mobile reference vs its own capture 95.37, 94.90, 95.10, 95.57, 92.96, 92.95 (5/6 below 95.57); desktop 96.69-98.09 (all above).
- Impact: accuracy of the gate, then time and completion: the mobile bar cannot be met reliably by the reference itself. Severity: **blocker** (it is the step the run stopped on).
- Root cause (high confidence): single-viewport calibration; a one-column phone layout reshuffles more of the page per draw. Alternative: none needed; the code path is explicit.
- Cause location: tool defect. R (tool): calibrate every unstable route at every scored size and for both layout and states (>= 3 loads each, min per size; store `unstable.byViewport`), use it in `report.mjs:213`. Test: re-capture heybhaskar; `meta.routes[/playground].unstable.byViewport.mobile` should be about 93-95; a re-score of this unchanged clone should pass mobile.

**BHASKAR-2: status has no honest exit for a step that no clone change can move**
- Category C, not previously documented (missing decision rule). Stage: fix loop -> end.
- Expected (skill:36-41): a step that does not move after three real tries is set aside, then Next, then exit 3.
- Observed: a try counts only if the clone changed after the step was issued and a newer score exists (`status.mjs:256-268`); the route step's command is `review --route /playground --size mobile`, which the tool answers "current, nothing changed" (`131-review-route-gate.log`): status names a step that cannot change anything. Routes have no Findings/skip path (interactions do: `status.mjs:240-241`) and no Accepted-differences path (`report.mjs:205-227` never calls `acceptedFor`). On a noisy value even real tries can reset the counter by a random "gain" of more than 0.5 (`status.mjs:265`; I: inference). Next is only reached after every candidate passes or is set aside (`status.mjs:271-284`), so nothing after the route (4 interaction scenarios, 2 of them tool-only) or Next was ever issued.
- Impact: run cannot reach exit 0 or 3 honestly; no Next.js app, no REPORT.next.md. Severity: **blocker** (with BHASKAR-1). This is a tool failure by test-plan section 4 ("status names a step that cannot be done").
- Cause location: missing decision rule (tool) + skill wording (the real-blocker clause invites a stop where a set-aside was intended).
- R (tool): when a route is `unstable` and below its bar, issue "write under ## Findings why route X cannot be held to its draw, with N reference draws as evidence" and treat the route as set aside once Findings names it with an existing evidence file (mirror the tool-only interaction path). R (skill): "a tool defect on one step is a set-aside, not a stop: write it in Findings and keep following status; stop only when status itself cannot run." Test: on this folder (no clone change), add the Findings line, run status: it should move to the interaction steps, then `next --verify`, then exit 3.
